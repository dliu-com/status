Technical architecture

Every 15 minutes, status.dliu.com visits each dliu.com site the way a guest would (no sign-in, no cookies) from Ireland, Virginia (US) and Tokyo, and decides whether each of its functions is up, degraded or down.

Three locations

Each check runs from Ireland, Virginia (US) and Tokyo, so a problem near one place doesn't look like an outage, and a problem only one place sees still shows up.

Passes everywherepass
Fails from one placedegraded, e.g. "fails from Tokyo only"
Fails from most placesfail

Up, degraded or down

Upevery check passed
Degradedslow, failing from one place, reported "warn", or failed once
Downfailed two runs in a row
  • A site is down when one of its essential functions is down, and degraded when any function isn't fully working (an optional one, such as Docs, being down only makes it degraded).
  • A failed check is tried again 2 seconds later in the same run, so one lost request doesn't count.
  • Availability counts degraded as available; only down time lowers it.
  • Private sites are checked too but not shown here.
  • The checks never count as visits on traffic.dliu.com.
Technical details
PartWhat it is
ScheduleEventBridge rule rate(15 minutes) in eu-west-1, no retries.
CheckerLambda (Node.js 22, arm64, 256 MB, 120 s) in eu-west-1. Runs the checks itself (Ireland), calls the probes, merges, judges, and writes the state and /data/status.json.
ProbesLambda dliu-status-probe in us-east-1 and ap-northeast-1 (stacks StatusProbe-us, StatusProbe-jp): same code and checks, invoked synchronously, returns raw results. No permissions beyond its logs.
RequestsGET or HEAD, 10 s timeout, redirect: manual, no cookies or Authorization, user agent dliu-status-bot/1.0 (+https://status.dliu.com/docs). Four sites at a time, each site's checks in order.
CombiningPer check: fail when more than half the locations that answered failed; warn when some failed, or more than half were slow; otherwise pass, with the median time. /health functions are combined the same way. A probe that doesn't answer is left out.
Definitionconfig/apps.json in dliu-com/status, imported from each site's /docs/health.md; the contract is HEALTH.md.
StatePrivate S3 bucket: failure streaks, 90 days of daily counts per site, incidents, private sites included. Kept if the stack is deleted.
PageStatic files in a private S3 bucket behind CloudFront (origin access control), /data/status.json cached 60 s, pages no-cache.

Why no CloudWatch metrics

Reading Lambda and CloudFront metrics for every site every 15 minutes would cost about $2 a month with GetMetricData, over the limit. The checks are instead purely what a guest sees, plus each site's own /health.

Security

status.dliu.com is a guest: it can't sign in to, change or read the private data of any site, and its page shows only whether things work.

No sign-inno cookies, tokens or passwords anywhere
Read onlyGET and HEAD; never changes anything
Least accessno AWS access to the other sites
Nothing private shownstatus only; private sites left out

What could go wrong, and what stops it

RiskProtection
The checker is misused to change a siteIt only sends GET and HEAD, without cookies or credentials, and doesn't follow redirects. A test fails the build if a check uses another method, adds headers or a body, or points at another host.
Its AWS role is misusedThe checker may only read and write its own state file, write data/* on its page, and call the two probes. The probes have no permissions. Nothing can read the other sites' databases or storage.
The page leaks private detailsIt publishes statuses and short generic reasons only: no response bodies, no identifiers (JSON values checked by pattern are never echoed), and private sites (jh.dliu.com) are left out of the public file entirely.
Script injection on the status pageStrict Content Security Policy (scripts from this site only, no inline), every value written with textContent (a test forbids innerHTML), framing denied, HSTS.
Using status.dliu.com to flood a siteThere is no way to start a check from outside: only the schedule runs them. Each site's /health is cached 60 s at CloudFront.
Someone hides from traffic.dliu.com by faking the checker's user agentAccepted: they only hide their own visits, and such traffic already counts as a bot.
Technical details
  • Both buckets block all public access, use SSE-S3 and refuse non-TLS requests. CloudFront reads the page bucket with origin access control.
  • IAM: s3:GetObject/PutObject on state.json, s3:PutObject on data/*, lambda:InvokeFunction on dliu-status-probe in us-east-1 and ap-northeast-1. The stack test fails if CloudWatch, DynamoDB, CloudFormation or wildcard S3/Lambda permissions appear.
  • Headers: Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' https://files.dliu.com/dliu.com/ui/; img-src 'self' https://files.dliu.com/dliu.com/; connect-src 'self'; frame-ancestors 'none', X-Frame-Options: DENY, Referrer-Policy: no-referrer, HSTS one year.
  • Logs are kept 90 days and contain the one-line summary per run, not response bodies.
